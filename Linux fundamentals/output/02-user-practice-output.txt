=============== 0. Which adduser does this box have? ===============
/usr/sbin/adduser: Perl script text executable
Perl script  = Debian/Ubuntu wrapper (the good one).
Symlink to useradd = RHEL family, no wrapper behaviour.

=============== 1. The blunt way: useradd with no options ===============
--- /etc/passwd entry ---
u_bare:x:1001:1001::/home/u_bare:/bin/sh
--- home directory? ---
ls: cannot access '/home/u_bare': No such file or directory
--- password set? (2nd field: ! or * means locked) ---
u_bare:!

No home directory. No password. Shell is whatever /etc/default/useradd says.
The account exists but cannot really be used. This is the classic gotcha.

=============== 2. useradd done properly (what you'd use in a script or Dockerfile) ===============
u_flags:x:1002:1002:Scripted User:/home/u_flags:/bin/bash
total 20

-rw-r--r-- 1 u_flags u_flags 3771 Mar 31  2024 .bashrc
-rw-r--r-- 1 u_flags u_flags  807 Mar 31  2024 .profile
Now it has a home and a shell — but still no password until you run passwd.

Other checks worth knowing:
  sudo chage -l tester      # password aging
  ls -la /home/tester       # /etc/skel files copied in
  su - tester               # actually log in as them

########## ADDENDUM — steps 5 and 6, run by hand ##########
# The script asks its questions with read from stdin. adduser consumed the rest of
# stdin on this non-interactive run, so steps 5 and 6 saw EOF and were skipped.
# Same commands, run directly:

$ usermod -aG sudo tester
$ groups tester
tester : tester sudo users

# The -a is mandatory. Without it, -G REPLACES every supplementary group:
$ usermod -G users tester      # deliberately WITHOUT -a
$ groups tester
tester : tester users
# sudo is gone. That is how people lock themselves out of their own box.
$ usermod -aG sudo tester      # put it back
tester : tester sudo users
